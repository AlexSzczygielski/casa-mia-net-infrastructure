# Home Assistant

Smart home automation platform. Bridge-networked, proxied through Caddy like
every other service — no host networking, no auto-discovery.

## Configuration

Split between two layers, not fully declarative:

| Layer | Format | Committed? |
|---|---|---|
| `config/configuration.yaml` | YAML, hand-edited | Yes |
| `config/secrets.yaml` | YAML, hand-edited | No — gitignored, holds credentials |
| Everything else (`.storage/`, `home-assistant_v2.db`, `automations.yaml`, `scripts.yaml`, `scenes.yaml`, etc.) | JSON/YAML, generated by HA | No |

> [!NOTE]
> Home Assistant moved most integrations off static YAML onto UI-driven
> **Config Flow** years ago — pairing, OAuth tokens, and discovered device
> IDs don't map cleanly to a file a person hand-edits. That state lives in
> `.storage/`, which also holds the auth token signing secret, so it isn't
> committed for the same reason `.env` files aren't elsewhere in this repo.
> `automations.yaml`/`scripts.yaml`/`scenes.yaml` follow the same logic:
> they're writable by the Settings UI, so committing them would drift from
> what's actually running the moment they're edited outside git. If that
> changes — hand-writing automations instead of using the UI — they can
> move into the committed set the same way `configuration.yaml` did.

Only `configuration.yaml` and `secrets.yaml` are mounted individually on top
of the bulk `/opt/docker-data/homeassistant/config` mount; both must exist
as files (not directories) on the host before `docker compose up`, or
Docker will auto-create them as directories and the container will fail to
start with a bind-mount type mismatch.

```bash
touch homeassistant/config/secrets.yaml  # if not already present
```

## Network mode

Plain bridge — no `network_mode: host`, no `privileged`, no `/run/dbus`.

This means no mDNS/SSDP auto-discovery (Chromecasts, HomeKit devices, some
smart plugs won't self-discover; integrations are added manually by IP or
cloud API). Traded deliberately for consistency with every other service in
this repo — same Caddy proxy pattern (`reverse_proxy homeassistant:8123`
by container name), no special-cased Caddyfile block, no Bluetooth planned.

## Reverse proxy trust

Unlike the other services behind Caddy, Home Assistant independently
validates the reverse proxy's origin and returns `400 Bad Request` for
anything it doesn't trust — the Caddyfile block alone isn't sufficient.

```yaml
# configuration.yaml
http:
  use_x_forwarded_for: true
  trusted_proxies:
    - 172.16.0.0/12
```

`172.16.0.0/12` covers Docker's default bridge subnet range rather than a
single IP, since Compose doesn't guarantee Caddy the same internal address
across recreates. Scoped safely — that range only exists on the Docker VM's
internal bridge network, unreachable from the LAN or internet.
